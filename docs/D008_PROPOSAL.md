# D008 proposed contract: operational research and protected evaluation

Status: proposed, pending actual Fable and Opus council responses and recorded dispositions. The five native perspectives are complete. Reversible implementation may proceed, but this proposal does not authorize final-data access, statistical certification, live orders, or an acceptance claim.

## Decision and sequence

Build two separately tested tracks. First, run the five persistent research roles against explicitly development-only evidence, with issued identities, typed capabilities, exact handoffs and searchable failures. Second, build a reservation-first evaluator whose data cannot enter those roles' normal tool or context paths. A later future campaign can use that boundary after an actual candidate freezes. Do not postpone operational research until future observations exist; do not turn the already exposed D007 interval into a holdout.

The five advisers agree on this separation. Evaluation recommends a frozen future champion and separate integrity/statistical/readiness axes. Data-boundary review shows why the explorer cannot protect a suffix: registration and admission read the entire acquisition. Roles recommends durable assignments and a deterministic tool broker; operations requires effect fencing, ambiguity preservation and tested restore; scope requires a real five-role historical workflow, not five renamed chat assistants. Reports are design evidence, not implementation certification or statistically independent votes.

## First increment: durable role workflow and memory

Use a fixed first-stage sequence: director, hypothesis researcher, experiment engineer, data/implementation critic, statistical/portfolio critic, then separate quality and scope oversight. Director freezes the bounded question and authorized development evidence; researcher records a falsifiable proposal and retrieved failures; engineer submits a strictly supported experiment specification; critics inspect exact upstream artifacts in separate contexts. The producer cannot select its reviewer identity or overwrite a finding. Quality and scope remain distinct from the five research roles.

Quanto issues each role assignment and random private capability token. Persist the token digest, actor identity, role-policy version, requested model/backend, exact allowed inputs, context/output schemas, step/time/output/spend bounds and upstream handoff identities before dispatch. Actors derive from the issued assignment; model-supplied identity strings never establish authorship. Assignment authority protects cooperating callers, not against the owner rewriting files. A common model/provider/lead can still cause correlated errors.

Use a journal-backed run and immutable stage attempts. Jobs carry leases and monotonically increasing fences. Check the current actor, lease, cancellation state and fence before every tool intent, provider dispatch and publication; final-completion checking alone is insufficient. Register each intent before its effect. Result publication verifies exact artifact bytes and commits the handoff plus terminal stage state atomically. A stale worker cannot publish after another incarnation takes over. Cancellation prevents later effects; an already sent call remains a potentially billed, uncertain attempt.

Recover only work demonstrably before its effect boundary. A provider dispatch followed by process death is uncertain, never automatically repeated. A deterministic study interrupted after its registered launch remains linked to that attempt; an explicit replay has a new attempt identity. Invalid, rejected, failed, cancelled and uncertain outcomes remain visible. A changed specification or context creates new lineage, not an overwritten stage. Each role gets bounded turns; exhausting a bound is a recorded stop, not permission for an autonomous retry loop.

The deterministic capability broker accepts strict typed requests with a unique request ID, assignment token, lease/fence and exact approved references. Initial operations are failure retrieval, development evidence inspection, supported-specification validation, registered development execution and artifact-linked review submission. No arbitrary paths, shell, SQL, model-selected provider endpoints, acquisition credentials, broker orders or protected evaluator capabilities. Unknown keys/actions/references refuse before side effects. Persist allowed tool requests and rejected attempts without secrets.

For the first real workflow, the owner-authorized deterministic supervisor supplies the already registered D007 development study and reviewed source-use envelope. Model roles may inspect only sanitized method, lineage and integrity facts expressly allowlisted for external transmission. Prices, provider records, private rules/results and protected artifacts stay local. If broader model inspection lacks rights or owner authorization, that limitation is recorded; no reviewer claims to have inspected undisclosed evidence. A model may propose or reject a generic supported research rule; the supervisor must bind any accepted rule to a new registered development attempt and preserve full acquisition/policy lineage. Reusing a completed calculation alone does not demonstrate an operational experiment stage.

Default operational text roles use the existing bounded API transport with a new explicit research-purpose allowance (USD 4/day maximum, within the shared USD 20/day global cap, never additive). Small bounded roles use exact Haiku; more demanding criticism may use exact Opus only within remaining budget. Requested models are frozen per assignment; no fallback. This does not alter the user's council preference: actual Fable and Opus council reviews use local Claude Code OAuth, tools/customizations/MCP disabled, without project API keys. Native build/review agents are not installed unattended workers. The common role contract supports future text transports without weakening authority or accounting.

Failure memory starts with structured queries over registered unsuccessful attempts and append-only repair dispositions. Index kind, status/code, submission/attempt, relevant code/data/specification identity and exact artifact references. Bound queries and results. Return original evidence identifiers and distinguish unresolved failures from a correction; never delete or overwrite the original. Record the query and selected failures in the hypothesis input. Matching a prior failure requires an explanation for repeating it, not a permanent veto. No embedding service or new subscription.

## Protected evaluator: separate acceptance gate

The legacy explorer remains development-only. A new evaluator namespace owns reservations, acquisition responses, normalization, source admission, results, partial responses and detailed errors. Ordinary roles, dashboard context and general artifact readers must not retrieve them. The initial same-user implementation can claim cooperating-application controls only; hostile-owner isolation requires a separately controlled OS identity/service and is a later deployment gate, not a claimed property of filesystem labels.

A reservation freezes economic-security identity/aliases; data/feed/adjustment and revision policy; acquisition envelope, warmup and final sessions; candidate/code/dependency identities; starting state, timing, benchmark and complete cost cases; source-use policy; authorized actors and fixed release schema. Existing or uncertain overlapping exposure across aliases/revisions refuses protected status. Registry checks apply at every acquisition and import entrypoint, not only an evaluation wrapper. Keep original full-acquisition replay and action/calendar checks inside the evaluator; a changed financial policy after access invalidates that campaign.

Commit one-use consumption before any protected acquisition, read, inspection or calculation. Pre-access refusal can remain unconsumed only with evidence no protected access occurred. Crashes, partial responses and unknown access consume conservatively. Exact replay verifies the same frozen invocation with a new execution attempt; changed code/data/rules produce diagnostic lineage and never restore the entitlement. Public receipts expose only fixed integrity/lifecycle states, identities approved by the disclosure policy and predetermined release times. Data-bearing quality diagnostics, dates, anomalies and intermediate results remain private. A failure cannot justify searching successive final windows until one passes.

First prove access control with synthetic fixtures and independent bypass/crash/restart/leakage review. Then reserve one mechanically selected historical access-control pilot outside existing acquisitions before requesting its data. This establishes application controls, with unknown owner/model prior exposure; it is not an unseen performance test. A final campaign must freeze a candidate before future observations begin. Neither pilot nor future campaign may be claimed started until it is actually registered, and future results stay pending until observed.

## Statistical and execution gates

Keep integrity, statistical conclusion and operational readiness separate. A benchmark CAGR/Sharpe comparison does not establish an edge, and failure to reject is not proof of no edge. The first future campaign permits one frozen champion, one primary benchmark and cost case, a complete search/failure roster, fixed observation/release horizon, worthwhile-effect threshold, dependence-aware uncertainty and preallocated campaign error allowance. Sensitivity scenarios and replays are not independent discoveries.

The evaluation adviser proposes daily net excess-return inference using Newey–West, an explicit power calculation, a 252-session policy floor and decreasing campaign alpha. These are proposals requiring a concrete estimand/sample plan and independent implementation/calibration review before final use. D008 does not accept a universal statistical recipe or automatic promotion rule merely by naming those methods. Record model-training and outside-search uncertainty. Any correction after outcome exposure starts diagnostic lineage.

Experimental prospective paper operation may begin after operational checks with efficacy explicitly unproven. It requires timestamped signals before eligible fills, positions/cash/orders reconciliation, realistic restrictions/costs, retained outages and a frozen assessment horizon. Live readiness adds separate credentials, limits, emergency stop, restart/reconciliation tests and a concrete reviewed strategy. Actual live activation always requires explicit owner approval. Crypto remains a separate later source/accounting scope.

## Independent acceptance and durable operation

First role increment acceptance: concurrent and stale capability denials; complete all-attempt lineage; actual five model roles completing one bounded historical development workflow with a genuine registered calculation; preserved objections and retrieved failures; exact independent critic, quality and scope reports. Synthetic role scripts alone cannot close R14. Insufficient funds leave real-model acceptance pending while local implementation continues.

Next evaluator acceptance: denied ordinary access, alias/overlap rejection, concurrent one-use consumption, pre/post-access crash evidence, exact replay and diagnostic correction, full calendar/action replay, no protected values in model packets/dashboard, then the witnessed historical access-control pilot. Statistical/future acceptance remains separate.

Before unattended research, test restart/reconciliation, cancellation, exhausted budget, wrong/truncated model output, missing/corrupt artifacts and consistent backup/restore against an externally preserved event-chain checkpoint. Restoring must not reset exposures, uncertain holds or dispatch entitlements. The website LaunchAgent and five-minute status capture already operate while this Mac is awake and signed in; that is not a research scheduler or 24/7 host guarantee. Dashboard assignments and diagrams should use durable workflow state when available and label existing native progress as lead observations.

No purchase, new subscription, raw market data transmission, live order or unsupported completion claim is authorized by this proposal.
