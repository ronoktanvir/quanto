# D012 proposed development-store reattachment after restart

Status: proposal only. No authority reattachment, configuration edit, research acquisition or calculation has occurred. The owner confirmed that the Mac restarted. The immediate objective remains D011's finite historical cost screen; this repair must not become a replacement research objective.

## Observed failure and scope

Read-only checks found that the persisted control configuration exactly matches the count and digest in the retained pre-run authority receipt. The original root, object directory, research database and control database retain their recorded inode, owner and permission values. All four report a different filesystem device number. The root path still matches; the store remains nonsynthetic and legacy-unknown. The existing supervisor compares the persisted device number and therefore cannot attach. No production D011 manifest has been registered.

The owner's restart report is consistent with renumbering, but neither that report nor matching file metadata proves complete data continuity or absence of rollback. Apple documents that filesystem device identifiers can change across restarts and distinguishes them from persistent volume identity. [File System Events guide](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html). A new persistent identifier measured today cannot retrospectively establish a value that was never recorded.

This is a narrow administrative recovery of cooperating development access on the same owner-controlled Mac. It cannot remove legacy exposure, grant protected acquisition, restore consumed dispatches, reconcile uncertain spending, certify external freshness, or enable unattended/live operation. No resource purchase, model fallback or extra market-data transmission is proposed.

## Proposed recovery contract

Keep the original configuration, store/principal identities, all application/control rows and audit history unchanged. Do not rewrite the old device value or create a replacement authority. Record any accepted device mapping as an additional explicitly reviewed administrative receipt in the existing control store, linked to its prior audit head and the retained evidence. Ordinary supervisor opening remains fail-closed unless the current device matches either the original binding or an exact accepted mapping.

Before recording that mapping, require a finite metadata-only preflight: exact existing paths and private permissions; same non-device physical identities as the retained receipt; exact original configuration/schema fingerprints; valid complete control audit chain and research journal chain; retained historical table prefixes and relevant terminal checkpoints; and a bounded inventory of active cooperating research workers. No worker may run during the reattachment. A prefix or checksum mismatch must refuse without rewriting evidence. Preserve unresolved/unfinished effects and every spending hold as found. Failure or missing evidence does not authorize a fresh store.

Freeze the concrete preflight, selected source and exact mapping before a one-shot administrator invocation. The transaction must recheck the frozen state and append the mapping plus audit evidence atomically. Use an exclusive attempt record, bounded process supervision, no automatic retries, and a read-only reconciliation path for uncertain completion. Reopen the same authority in a fresh process and verify old data/state plus the new mapping. Tests must show unchanged exposure, reservation, consumed-run, budget and legacy flags; changed path/inode/owner/configuration, stale preflight, replay, partial writes and conflicting mappings must refuse.

The implementation should be small. An audit-bound append-only mapping table is a candidate, not a settled mechanism; advisers should compare it with a separately pinned administrative receipt or a narrowly scoped session attachment. No design should silently ignore device identity on every open or monkeypatch filesystem results. Runtime physical checks still bind the actual current device/inode during each process.
