# Registered exploratory research

`quanto.explorer` connects private artifacts to the deterministic research engine with recorded submissions, explicit dataset registration, common evaluation windows, and development exposure history. Synthetic fixtures use the original calculation path. Historical raw prices require a separate evidence-bound admission and use the D006 event engine. Neither path establishes a validated strategy, a protected holdout, or a complete research operation.

Historical registration manifests remain `inspection_only` permanently. `admit_dataset` creates a separate content-addressed record granting only `conditional_retrospective_development` calculation. The runner revalidates that record and all dependencies before and after a historical calculation. A supplied approval flag cannot override the gate; current revisions and attributed judgments do not establish point-in-time knowledge or universal event completeness.

## Submission and dataset contract

Both `register_dataset(root, request)` and `run_submission(root, request)` accept a dictionary or bounded raw JSON text and return a receipt dictionary. Dictionary requests are serialized once; the resulting bytes are the same bytes hashed and parsed. Raw JSON is hashed exactly as received. The submission is committed before JSON parsing, semantic validation, Bar construction, or StrategySpec construction. Malformed JSON, duplicate keys, nonfinite values supplied as text, invalid fields, missing data, and unsupported assumptions produce retained outcomes with fixed reason codes. Raw submitted content and arbitrary exception messages are not retained.

The provenance boundary accepts at most 64 KiB of UTF-8 request text. Oversized text, unsupported Python objects, unserializable dictionaries, or invalid Unicode cannot cross that boundary and do not have a submission receipt. A hash-only submission identifies the request without providing its contents for replay; preserve an approved request separately when replay is required. See [PROVENANCE.md](PROVENANCE.md) for the storage and privacy threat model.

Dataset registration accepts exactly:

| Field | Meaning |
| --- | --- |
| `data_sha256` | Existing JSON artifact identity; its actual bytes are read and verified. |
| `evidence_kind` | `synthetic_fixture` or `historical_market_data`. |
| `market` | Exactly `instrument_id`, `venue`, three-letter `currency`, and IANA `session_timezone`. |
| `price_basis` | Explicitly `raw` or `all`; computation requires raw prices and, for historical data, separate admission. |
| `expected_sessions` | Ordered ISO date list, mandatory for synthetic fixtures; if supplied it must exactly match all source bar dates. |
| `parent_dataset_sha256` | Optional registered parent for the same declared instrument. |

The source may be a bar list or a JSON object containing `bars`. Every bar requires timestamp, symbol, open, high, low, close, and volume; an optional source timestamp is retained in the source artifact. Normalization constructs typed `Bar` values, rejects nonfinite/inconsistent prices and duplicate or unordered dates, and converts aware timestamps into the declared session timezone. Explicit source-envelope evidence, price basis, symbol, currency, and timezone must agree with registration metadata. No missing bar is filled or substituted.

A successful registration writes a normalized artifact and a manifest with their actual hashes, the source hash, exact dates, coverage, evidence classification, financial limitations, and admission state. Its receipt includes verified direct references to all three artifacts. Synthetic instruments require a `synthetic:` identifier. Historical instruments cannot use that prefix. Classification of a bare caller-supplied list still relies on the caller; these controls do not authenticate a provider or prove that synthetic data are synthetic.

The registration manifest's `coverage_start` and `coverage_end` describe returned bars. Its `exposure_start` and `exposure_end` cover the full provider-requested interval when supplied, including dates for which no bars were returned. Otherwise the complete returned range is used. An exact synthetic schedule tests fixture coverage; it does not verify an exchange calendar. Merely providing an expected date list cannot admit historical data.

## Fixed windows and execution identities

A study request contains `dataset_sha256`, `study_name`, `evaluation_start`, `evaluation_end`, and `specification`. Historical studies additionally require `admission_sha256`; synthetic studies reject that field. The specification is the existing `StrategySpec` object: lookback, entry and exit thresholds, starting cash, and per-fill cost in basis points. Defaults are frozen into the recorded specification.

Every candidate evaluates exactly the requested inclusive dates. For a lookback of `L`, the runner selects exactly the `L` registered sessions immediately preceding the evaluation start, followed by the common evaluation window. It rejects missing boundaries or insufficient preceding sessions. Two lookbacks therefore share benchmark dates and benchmark accounting while using their own required warmup. A longer lookback cannot silently shorten the tested period. The strategy starts in cash, and the last warmup close can first affect an order at the evaluation window's first open. Warmup does not simulate an inherited portfolio.

Before computation, the runner registers a fingerprint of the normalized specification, verified dataset identities, assumptions, and code identity, then registers an attempt linked to its submission. The code identity includes current source-file hashes, including uncommitted contents, the available dependency lock hash, interpreter version, the actual engine entrypoint's bytecode, and loaded research helper functions and class methods, including normalized positional and keyword defaults. Function defaults bind their code recursively with cycle refusal; class defaults bind their qualified identity. Other unsupported function-default objects are refused. This distinguishes an old imported helper from a changed source file that has not been reloaded. The identity also binds the D006 event engine entrypoint, loaded helpers and imported Quanto helper functions, policy globals and actual numerical policy, plus admission and acquisition source files and their loaded validation/replay helpers and policy constants. Function identity does not depend on the function declaring a Quanto module, so replacement lambdas and imported helper aliases are included. Source and loaded-code identities are checked again after execution. These identities aid reproduction; they do not attest the complete machine, imported native libraries, mutable arbitrary process state, or a malicious owner.

A successful result is a content-addressed artifact containing the complete engine report and frozen specification/data/code identities. The artifact and its referenced dataset objects must be published and verified before success. The attempt and submission outcomes commit in one journal transaction. A publication error cannot leave a successful attempt paired with a failed submission. If an observed publication interruption can be recorded, the submission is `interrupted` and its attempt is failed with a fixed reason; if storage itself cannot accept an outcome, the API returns a fixed safe pending response and work remains pending. Published but unclaimed artifacts may remain after a rollback.

Results say `exploratory_result`, preserve the engine's `unprotected_not_implemented` holdout status, and mark `investment_evidence: false`. There is no `DATA VALIDATED`, `NO EDGE`, profitability, or protected-final verdict. The existing engine's timing and accounting limitations remain attached to its report.

## Candidate counts, retries, and exposure

Study names are labels rather than candidate identities. Repeating the same normalized rules, dates, data, and code under a new name creates another execution of the same fingerprint. `recorded_candidate_count` counts distinct executed fingerprints for the declared instrument; `recorded_execution_count` counts registered executions, including unfinished or failed ones. Requests rejected before an execution is registered remain submissions rather than being falsely counted as executed candidates. Changed data or code create a distinct fingerprint. These are application counts, not estimates of every idea the owner has considered.

Registration and exploratory access append development exposure records. The entire registered/acquired range is `development_only`, with prior exposure `unknown_outside_application`. This includes warmup and any additional loaded or selected dates, not just the displayed evaluation interval. Exposure survives a failed run, a renamed study, a changed parameter, and revised data bytes. An optional parent manifest records a known revision relationship; overlap is still found without a supplied parent.

`list_exposures(root, market, start, end, limit=100)` returns inclusive date overlaps. Matching conservatively uses the case-insensitive declared instrument identity; changing venue, feed-related naming outside that identity, currency, or study name does not clear existing overlap. Original market metadata and dataset identities remain in each record. Alias resolution and stable issuer identity are not implemented, so changing the instrument identifier can obscure a relationship. No identifier or empty query establishes that an interval was unseen.

Exposure records are append-only application tables with events in the journal's hash chain. They are not OS isolation, access authorization, or immutable storage. Direct file reads outside this API, previous charts and model training, provider revisions, omitted acquisitions, and a database owner can escape these controls. The complete acquisition request is separately retained by the acquisition receipt; an interrupted registration before it can identify a valid dataset may have no explorer exposure row. That absence cannot be used to certify a final interval.

## Conditional historical admission

`admit_dataset(root, request)` takes a dict or bounded raw JSON and records a submission before semantic validation. It returns `admission_sha256` only after successful evidence checks and publication. `validate_admission(store, admission_sha256, dataset_sha256)` repeats those checks against retained exact bytes and current code; callers cannot replace dependencies under an existing identity.

Admission requests have exactly these fields:

| Field | Required evidence |
| --- | --- |
| `dataset_sha256` | Existing registered historical raw-price manifest. |
| `bars_receipt_sha256`, `calendar_receipt_sha256`, `actions_receipt_sha256` | Successful acquisition receipts linked to their actual successful submissions. |
| `submitted_requests` | Object with `bars`, `calendar`, `actions` hashes of the exact original submitted request bytes, matching each submission's hash and size. |
| `primary_facts_sha256` | Attributed issuer identity, scoped coverage assessment and event-term extraction, referencing retained source bytes. |
| `usage_review_sha256` | Attributed interpretation of retained actual source-use materials for the authorized private purpose. |

The verifier reparses each original request, reproduces normalized request parameters and exact page URLs, checks page/status/byte/pagination bounds, reads every raw page, replays normalization, and compares normalized rows with stored artifacts. Bars must use daily SIP USD raw prices with `asof=-`. Calendar requests must cover the identical full acquired interval; their ordered session dates must exactly equal all acquired bar dates. Dataset source, normalized bars, metadata and full-range exposure must match. Actions must request all categories, US region, `data_quality=all`, and the declared 2016-to-acquisition-date process envelope. A fully paginated empty response means no returned events, never absence proof.

The primary-facts document has `schema_version: 1`, `kind: attributed_primary_facts`, `reviewer`, aware ISO `reviewed_at`, and `sources` containing `sha256`, HTTPS `url`, `title`, and `locator`. An optional `receipt_sha256` links a `public_source_receipt` to a successful `public_source_observation` submission and must match the exact source hash and URL. This establishes retained observation metadata, not machine authentication of issuer assertions. Each identity/coverage/event judgment includes `source_sha256`, `locator`, and an explicit `judgment` tied to an actual source document, not merely to a receipt.

The `identity` judgment supplies `symbol`, `instrument_id`, `issuer_name`, `currency: USD`, and continuity boundaries covering the acquired interval. The `coverage` judgment supplies exact acquired `start` and `end` and a `known_events` list reconciled against the derived events. `events` contains each relevant `provider_id`, its canonical `event`, and the attributed source judgment. Split events use `kind: split`, `event_id`, `effective_date`, `new_rate`, and `old_rate`; effectiveness must match provider `ex_date` and issuer first post-split trading terms. Cash-dividend events use `kind: cash_dividend`, `event_id`, `ex_date`, `payable_date`, decimal-string `rate`, `currency: USD`, and `share_basis: ex_date_shares`.

Dividend annotations require `provider_rate_basis: ex_date_shares` or `pre_split_shares`. The latter also requires `conversion_split_event_id` referencing a corroborated relevant split, with an attributed conversion judgment. The verifier compares rates as exact rational values: pre-split rate multiplied by old/new split units must equal the issuer ex-date-share rate. Missing/empty provider currency can be resolved only by the explicit issuer USD judgment; a conflicting non-USD currency rejects. Unsupported dividend flags, due bills, unresolved rate basis, or mismatched date/rate terms reject.

Relevance covers every acquired session, including acquired rows outside the selected calculation subset. Associated payable dates remain relevant after the acquired end. Unknown categories, unknown ex/effective dates and identity-change records are not silently discarded. Rule version `D006-admission-v1.1` permits only the narrowly evidenced pre-window buyer-side cash-merger exclusion described below; all other identity-change records still reject. Known nonidentity categories with valid ex-dates strictly outside the acquired interval may be excluded; relevant unsupported categories reject. Provider symbol conflicts, inconsistent nonempty CUSIP or ISIN identifiers and same-session multiple actions reject conservatively. Exact same-ID source records may collapse to one economic event while all occurrences remain in source evidence. Conflicting same-ID records and multiple IDs for the same economic event reject.

A cash-merger record can describe the studied issuer purchasing a different security, rather than converting the studied shares. The initial unconditional identity-event refusal was therefore broader than the D006 structured-relevance rule. The `completed_acquirer_only_source_bound_v1` subpolicy permits an exclusion only for `cash_mergers` whose provider `effective_date` is strictly before the full acquired interval, whose acquirer is the queried symbol, and whose separately identified acquiree is a different symbol. It does not add merger accounting or change the strategy, warmup, evaluation window or cost assumptions.

The optional `primary_facts.excluded_actions` list requires exact annotations with these fields:

| Field | Meaning |
| --- | --- |
| `provider_id`, `category` | The exact provider ID and `cash_mergers`; an event cannot be annotated both accepted and excluded. |
| `record_sha256` | SHA-256 of canonical JSON for the entire normalized provider `record`, excluding its wrapper and occurrence list. Every normalized field remains bound. |
| `effective_date` | Exact provider effective date, strictly earlier than the full acquired start. |
| `acquirer`, `acquiree` | Each contains exactly `symbol`, `cusip`, and `isin`, matching the corresponding flat provider fields. Absent optional identifiers are null, never invented. |
| `source_sha256`, `locator`, `judgment` | Retained issuer source and attributed participant/role/no-conversion interpretation. |
| `completion` | Object containing `date`, `source_sha256`, `locator`, `judgment`, `no_studied_share_conversion: true`, and `no_outstanding_studied_entitlement: true`. |

The completion source may differ from the participant source, but both must be retained in `sources`. Completion must fall on or after effective date and strictly before the acquired start. A supplied provider payable date must fall between effective date and completion and before the acquired interval. Missing or empty payment timing is excluded only under the explicit source-bound completion and no-outstanding-entitlement judgment. These assertions remain attributed extraction judgments; their Boolean fields alone cannot authorize exclusion.

At least one acquirer identifier must reconcile with the studied-security identifiers in the relevant event corpus; every supplied acquirer CUSIP and ISIN must match in its own namespace. An acquiree CUSIP is required by the supported provider schema. No supplied acquiree identifier may equal an acquirer or studied-security identifier in that namespace, even when the symbols differ. Missing roles, crossed identities, unsupported fields suggesting stock consideration, malformed cash terms, relevant/future dates, stock or mixed mergers, unmatched annotations and conflicting annotations reject. A positive cash rate is retained for schema consistency but is not applied to the studied portfolio.

The verifier checks duplicate IDs across the complete corpus before any exclusion. Exact same-ID duplicates collapse only after preserving every source occurrence. Conflicting same-ID records and multiple IDs for the same acquisition participants/effective date reject, including process-date revisions. Successful admission retains the full exclusion annotation, exact record hash, reason and all raw-page occurrence references. Source corruption, tombstones, changed facts or changed validation rules require refusal or a new admission; the original refused submission remains in the journal. No primary-source judgment, annotation or rule update overwrites the earlier decision.

The source-use document has `schema_version: 1`, `kind: source_use_review`, `reviewer`, `reviewed_at`, `sources` in the same retained-source format, `purpose: private_own_account_research`, `public_distribution: false`, `external_model_transmission: false`, an `interpretation`, and `unresolved` including `account_and_exchange_terms_not_certified`. This is a bounded attributed assessment, not legal certification. The admission record explicitly retains vendor-omission, current-revision, process-envelope, issuer-extraction, executable-price, fractional-share and protected-holdout limitations.

The frozen accounting policy uses exact rational signal comparisons and local Decimal precision 34 with half-even rounding for portfolio amounts. Splits change share units and rebase historical signal inputs only when effective. Dividends accrue from ex-date pretrade shares as nominal claims; later splits never multiply earned claims. Payment becomes usable at the first open strictly after its payable date, with modeled end-of-pay-date cash release. Both strategy and benchmark retain dividend cash, count unpaid claims at terminal value, and incur no invented final liquidation. The benchmark never redeploys dividend cash. Historical evidence kinds and admission identities persist in the experiment fingerprint, result and attempt outcome.

## Remaining operation work

A successful software test of admission uses synthetic source/issuer fixtures and does not establish real data adequacy. Actual historical calculation additionally needs observed provider and issuer artifacts and independently reviewed evidence. Calendar acquisition alone does not supply those controls. Comparing raw and adjusted prices can establish that no provider adjustment was observed in that comparison; it does not prove an absence of splits, dividends, revisions, or other corporate actions. Current data revisions and ticker identity cannot establish point-in-time or survivorship-free research.

Protected final evaluation needs a separate access boundary and independently reviewed exposure policy. This module does not implement either. Scheduled research, full research-role orchestration, independent reviews of actual strategy artifacts, performance statistics beyond the engine's current measures, and paper/live promotion are also separate unfinished requirements. This runner contains no network, scheduler, model call, credentials, or order placement.

Tests use temporary synthetic artifacts, including clearly labeled fake transport and issuer responses. They cover source replay, receipts linked to submissions, exact request and page parameters, cap/pagination refusal, calendar equality, rate-basis conversion, currency and identity conflict, retained duplicates, unknown/unsupported events, corruption and tombstones, public-source receipt binding, historical routing and reproducible replay. Existing common-window, exposure, interruption and atomic-publication checks remain. Passing these tests supports software behavior only.
