# Registered three-scenario studies

D007 studies require a registered complete roster before any member calculation. `quanto.study_suite` freezes exactly three requests, one each for integer costs of 0, 10 and 25 basis points. Every other request field, including study name, admission, dataset, evaluation dates and specification values, must match. This is a bounded workflow invoked by the lead; it is not the future unattended research scheduler.

## Registration and membership

`register_suite(root, request)` accepts a dictionary or bounded strict JSON text with one field, `members`, containing three complete exploratory study requests **without** `suite_sha256`. Each request has `dataset_sha256`, `admission_sha256`, `study_name`, `evaluation_start`, `evaluation_end` and `specification`. Each specification explicitly supplies `cost_bps`. Order at input is immaterial; the stored roster is ordered 0, 10, 25.

Registration starts a provenance submission before semantic validation. Malformed bounded input retains a digest and fixed refusal code, without retaining raw invalid text. The existing maximum request size and UTF-8 boundary apply before a submission can exist. A successful registration revalidates the admission and registered policy revision, checks each member against the revision's frozen study, verifies dependency bytes, and checks that a successful admission's actual journal completion preceded registration. It stores the exact accepted registration bytes and a content-addressed manifest containing the full requests and their canonical SHA-256 identities. The returned receipt includes `submission_id`, `status`, `suite_sha256` and `artifact_refs`.

`validate_membership(store, suite_sha256, study_request, before_submission_id=...)` rechecks the successful registration, original request bytes, full admission/revision dependencies, manifest and exact canonical member identity. The study request must contain the matching `suite_sha256`. When a current study submission is supplied, the registration's journal completion must precede that study's journal start; timestamps supplied by callers do not establish order. The return contains `suite_sha256`, `member`, the complete `members` roster, `policy_revision_sha256` and verified `artifact_refs`. Each member contains `cost_bps`, `request` and `request_sha256`; its manifest request excludes the injected suite identity. Membership alone does not authorize a calculation. The explorer also requires a pending complete suite invocation and its committed launch through `validate_launch`. Existing studies outside that profile remain governed by their existing admission route.

## Execution and deliberate replay

`run_suite(root, {"suite_sha256": digest})` starts a new provenance submission and revalidates the registered suite. Before dispatching the first calculation, it retains the exact run request bytes and stores a separate run roster containing all three actual requests, with `suite_sha256` injected, and all three canonical request identities. A committed append-only launch record with a unique `(run_id, cost_bps)` key precedes each `explorer.run_submission(..., suite_run_id=...)` call. The suite module does not call a calculation engine or network directly.

`validate_launch(store, run_id, request, child_id, bind=True)` checks that the invocation is pending, the retained run request matches its original submission bytes and suite identity, the entire run roster equals the registered suite, and the matching launch journal event preceded the child submission. It then binds that launch transactionally to the pending child before any calculation. A consumed launch cannot bind another child. The explorer rechecks the same binding after calculation. A directly submitted valid roster member without this invocation is refused, so it cannot produce an isolated result outside the complete suite accounting.

Each intentional invocation dispatches each member at most once. Invalid, failed, interrupted and pending child outcomes are retained alongside successful outcomes; none is filtered from the summary. An unexpected dispatch exception is recorded with a fixed code. Because the child state may be unknown, that slot remains pending and the suite remains incomplete. The workflow continues to the other scenarios when it can preserve their records safely. It never retries an uncertain member.

Calling `run_suite` again explicitly creates a separate replay invocation using the identical registered requests. It never resumes an old invocation. Each explorer child has its own submission and attempt identity; experiment fingerprints and result artifact identities remain the explorer's responsibility. The lead must compare all three exact result artifacts across deliberate invocations. A suite result alone does not certify deterministic replay, independent numerical agreement or investment performance.

## Completeness and crash inspection

The durable summary contains all three requests, identities and member outcomes. `complete` means every member has a known terminal outcome other than interrupted; `all_success` separately requires three successes. Known invalid or failed outcomes therefore produce a complete but unsuccessful suite. A pending or interrupted member produces an incomplete summary and an interrupted overall outcome. Summary artifacts and the final provenance outcome are retained privately.

`inspect_run(root, submission_id)` reconstructs every slot from the frozen run roster and recorded child receipts without executing anything. Discover pending invocations through `Provenance.list_submissions(kind="study_suite_run", status="pending")`. An abrupt process exit leaves a discoverable pending invocation with its roster; slots distinguish `not_started` from `launched`. A crash after child binding preserves that exact pending child identity alongside the other two slots. A crash between dispatch and binding can leave a launched slot with an unconfirmed child, but the calculation gate has not yet authorized that child. Both states remain pending and never authorize automatic recovery. Invalid requests that fail before binding are linked by the runner when their receipts return, preserving their refusals in the complete roster. Later child terminal receipts can be reflected by inspection; an older summary artifact remains the immutable-by-identity snapshot of its own publication time.

Append-only application tables and journal event checks constrain cooperating callers. SQLite and local files remain writable by their owner; these controls do not authenticate authors or resist an owner rewriting all records. Tombstoned or changed dependencies block new membership validation and execution. Previously frozen run rosters remain inspectable when only external dependencies are unavailable; tombstoning the roster itself blocks its retrieval.
