## Minimal permission correction

The reported `0644` database mode is consistent with the source-level failure mechanism. `Provenance` assigns `0600` only when it creates a new database; an existing file bypasses that branch. Both it and `Journal` can initialize or write SQLite before a later guarded content read rejects group/other permissions. Calling a constructor would therefore be an effectful and unnecessary permission probe.

The concrete `tighten-research-mode.py` at SHA `23a9b375cb12de8fc4398ea85a456d2c8bec18f907cbccd7bfc62cb3519305ea` is appropriately narrow. It requires the reported exact initial mode, owner, regular file and single link; rejects symlink paths and preexisting sidecars; writes an exclusive durable intent; opens a no-follow descriptor; binds its identity; applies `fchmod(0600)` and verifies the same descriptor/path identity and final mode. It contains no database-content read, SQLite constructor, bootstrap, provider, model or research invocation. No necessary source correction was found.

The required concrete action is this single descriptor-bound mode correction followed by clean outer-exit and receipt verification. It needs no database rebuild, content hash/replay or additional architectural council. A partial or uncertain outcome must remain recorded rather than retried. The operation does not certify concurrent content stability, and its result correctly leaves that claim false. Later application preparation must separately recheck its actual store/sidecar conditions; a successful mode correction does not clear those checks.
