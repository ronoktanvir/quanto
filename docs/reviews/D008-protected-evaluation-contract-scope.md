## Why the proposed boundary fits D008

The source confirms the gap the plan addresses. `alpaca_data._dispatch` checks route and credentials but has no reservation permit. Bars/calendar and actions persist prepared requests and page receipts, yet provider bytes can arrive before explorer exposure is recorded. `explorer.register_dataset` reads its object before publishing exposure. Ordinary provenance reads check object identity and tombstones, with no stable principal or evaluator namespace. `_market_key` resolves only a case-folded declared instrument identifier, while `issue_stage` generates a new actor identity for each assignment. None establishes continuous reviewer/selector identity or alias-safe reservation isolation.

The plan correctly retains development-only admission and packet schemas, separates the future evaluator store, preserves uncertainty, and defers the statistical plan. Its first useful result is a tested application access boundary and conservative records, not a claim that existing D007/D008 observations became unseen. The accepted policy requires both preventing access and preserving evidence of attempted access; neither a later backtest refusal nor an empty exposure query substitutes for those controls.

## Required implementation-contract precision

1. **Consume exact effect authority before each external page or content read.** The plan proposes effect-start records and permit checks; specify their atomic relationship. Bind an issued intent to the normalized request, page identity, stable principal, registry/identity revision and permitted scope, then durably consume the relevant one-use effect entitlement before I/O. A check followed by reusable authority is insufficient. Pending intents block conflicting reservations without a network-long database lock. Timeout, crash or missing terminal evidence retains uncertainty; no automatic page retry or new final opportunity follows.

2. **Make rejection and exposure distinct states.** A generic failed/cancelled outcome must not clear a conflict or restore an entitlement. Only an evidence-backed rejected intent whose access log establishes no emitted acquisition request and no opened protected file may remain unconsumed. A committed start followed by a crash is unknown access even if no response object exists. Preserve every attempted registration and refusal with bounded safe reasons. If audit storage is unavailable, deny the effect; do not proceed with an unrecorded access.

3. **Classify before reading, and keep unexpected coverage conservative.** Imports cannot open unknown bytes to discover whether opening them was allowed. Their prior classification must come from a reviewed supervisor-owned origin/coverage contract, not a caller-supplied `access_class`, root path, ticker or date claim. Bars, global calendars and action process-date envelopes require separate profiles. Unknown coverage remains ineligible for protected status. A later unexpected response/alias discovery must preserve widened uncertainty and invalidate affected protection before ordinary publication; filtering out inconvenient rows cannot restore an untouched-window claim.

4. **Bind principal and alias continuity to the same reservation/access cut.** Persistent principals are a prerequisite once real reservations/access are permitted, even if their evaluator UI arrives later. Assignment tokens, new role labels or credential reissuance must not create a new reviewer/selector identity. Pin evidence-bound economic-security aliases and principal relations to explicit revisions, recheck them at effect authorization, and retain later merges/revisions. Conflicting or unresolved continuity prevents protection; it must not reset historical access. Known old exposure should still permit a genuinely later, known non-overlapping interval, as D008 requires.

5. **Define the legacy reconciliation gate before eligibility.** Inventory provenance requests, prepared/page events, terminal and pending acquisitions, imported objects and explorer exposure, retaining original timestamps and uncertainty. Missing rows are not proof of no access. Unknown legacy identity/coverage blocks an eligibility claim until resolved under an explicit profile; do not guess a narrower interval from returned rows or mint a clean registry in another root. Reconciliation may begin with synthetic fixtures, but actual protected eligibility requires an observed, complete boundary for the relevant instrument/window.

6. **Name the guarded routes and close alternate application reads.** Guards must live in underlying acquisition/transport/import/read services, including injected transports and pagination, not just CLI wrappers. Pin the supervisor's registry/store identities and deny unsupported roots before protected bytes are opened. The route inventory must also address ordinary provenance lookups and administrative copy/inspection helpers before a future evaluator namespace is activated; a backup reader is still a reader. Pure numeric functions cannot recover secrecy after input disclosure. Until all claimed routes are integrated and tested, describe the result as registry/guard preparation rather than guarded application access or an available protected evaluator.

7. **Keep private control evidence separate from shared release.** Reservation manifests and access logs can contain sensitive instrument/window/actor relationships even without prices. Specify where they live and which fixed control fields may enter ordinary journals, status, failure memory, model packets and conversations. Complete manifests, readable protected-object references and data-dependent failure detail must not leak through generic metadata. Predetermined lifecycle release shape/timing must cover failure and uncertainty as well as success. Do not introduce a convenient new disclosure field as a routine UI change.

These clarify enforcement of the accepted contract; they do not add a new owner approval gate. The producer should freeze the actual state transitions, coverage profiles, identity bindings and route inventory before implementation acceptance. An incomplete ordinary-route integration can be retained as a foundation, but it cannot authorize real protected acquisition.

## Acceptance and threat-model limits

Independent checks must exercise both reservation/access race orders, authorization-to-dispatch gaps, repeated/page-specific permits, crash boundaries, unknown legacy evidence, alias/principal changes, rejected-unconsumed proof, alternate roots and protected-derived egress. The critical evidence is that refused paths perform no fake transport call or protected file open and that uncertain starts continue to block overlap after restart. Synthetic test results validate those software properties only; separate criticism, quality and scope must identify the exact implementation revision.

Same-user agents and the owner retain filesystem and process authority. Registry rows, directory markers, capabilities and permissions therefore control cooperating application paths, not a hostile local owner. Stronger OS/service isolation would require a separate concrete design and demonstrated denial. No local record proves absence of prior external human/model exposure or supplies trusted rollback protection.

No financial threshold, estimand, sample horizon, dependence correction, campaign-error method or profitability rule is accepted here. Those remain separately reviewed before a performance campaign. A historical access-control pilot still requires a pre-access mechanical selection rule/seed, proved application non-overlap and frozen integrity-only release schema; failure stays consumed. Full evaluator isolation, protected-source review, sustained roles/scheduling, external effect/restore barriers, prospective paper work and separately approved live execution remain incomplete. This foundation closes neither R13 nor R14.
