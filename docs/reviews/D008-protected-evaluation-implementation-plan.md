# D008: protected-evaluation implementation boundary

**Build the reservation and access-intent gate before adding a protected acquisition route.** The existing explorer records development exposure, but acquisitions and generic artifact reads can occur before that record exists. A wrapper around the backtest cannot close this gap. The next coherent increment should enforce interval reservations across the existing application entrypoints, preserve uncertain access, and explicitly leave real protected evaluation unavailable until the separate evaluator namespace is implemented and tested.

## Observed implementation gaps

| Boundary | Current source evidence | Required change |
| --- | --- | --- |
| Acquisition before exposure | `alpaca_data._acquire` and `alpaca_actions.acquire_actions` prepare requests, dispatch pages and store response bytes through ordinary `Provenance`; neither consults a protected reservation registry. | Register the exact normalized acquisition intent before dispatch and gate every page against the issued intent and reservation state. Interrupted and uncertain requests must remain visible to later reservation checks. |
| Import and ordinary reads | `explorer.register_dataset` calls `store.read_json` before appending exposure. `Provenance.read_bytes/read_json` check identity and tombstones, not actor or evaluation namespace. | Keep protected bytes out of the ordinary store; require classified origin/coverage before development import or ordinary access can establish non-overlap. An unknown object is not evidence of an untouched interval. |
| Interval and identity | `explorer._market_key` hashes only the case-folded declared `instrument_id`. Existing overlap queries are inclusive by date and survive price revisions/venue changes, but no stable alias mapping exists. | Add a versioned, evidence-bound economic-security/alias relation and interval-aware reservations. Feed, adjustment, renamed ticker, revised bytes or changed rule must not create a fresh entitlement. |
| Principal continuity | `ResearchWorkflow` issues capabilities and fences publication, but creates a new `actor_id` per assignment. The same person/agent can therefore appear under another role identity. | Bind protected access and selection exclusions to a supervisor-issued persistent principal, with recorded role and identity changes. An assignment token or caller-supplied name alone cannot establish reviewer-selector separation. |
| Protected admission and results | `admission.py` declares development-only scope; explorer and suite validators replay retained full acquisitions. `research.py` reports `unprotected_not_implemented`. | Preserve that behavior. Add a separate evaluator-owned admission/calculation path; never relabel the current historical pilot or protect only a suffix of already-readable pages. |
| Release and context | `research_packets.validate_packet` accepts only `sanitized_development`/`development_only`; website conversations read fixed project documents and status. There is no protected lifecycle release schema or schedule. | Keep current model schemas closed to protected data. Only supervisor-produced, predetermined lifecycle receipts may enter shared status/docs; detailed errors, intermediate metrics and artifact lookup references remain private. |

`cli.main` forwards the acquisition, registration, admission and suite commands to these functions. The gate belongs in the underlying functions, not just the CLI. Pure numerical engines cannot enforce secrecy once a caller possesses their input arrays; the service boundary must prevent ordinary callers from obtaining protected inputs.

## Smallest coherent next increment

Implement a local `evaluation_registry` module plus integration tests and mandatory guards in the existing acquisition/import paths. This is enforcement preparation using synthetic fixtures, not an actual reservation or historical pilot. Keep real evaluator acquisition disabled until the next namespace increment passes independent review.

The registry should append reservation manifests, identity/alias bindings, access intents, effect starts and terminal/uncertain outcomes. A reservation binds the accepted D008 fields: stable security and aliases; feed/adjustment/revision policy; acquisition envelope, separate warmup and final intervals; frozen candidate/code/dependencies and scenario identities; permitted actors; rights scope; and fixed disclosure/release contract. Do not invent a statistical decision rule to fill a missing field; an incomplete campaign remains ineligible for final use.

Use one short transaction to check conflicts and reserve either an interval or an access intent. Reservation creation must conflict with already-issued overlapping acquisitions/imports, including those between authorization and completion. Conversely, an ordinary access intent must conflict with an existing reserved interval. Holding a database lock across a network request is unnecessary: the retained in-flight intent supplies the conflict until an evidence-backed terminal outcome is recorded. Check the exact permit, page request and fence before each dispatch; a direct lower-level transport call without the required issued authority must not become an application bypass.

The existing normalizers provide request parsing, not complete exposure classification. Bars have symbol/date coverage; calendar requests have no security identifier; action requests use **process-date envelopes**, which do not establish the economic dates of returned events. Define separate typed coverage profiles and fail closed when the relevant coverage or identity is unresolved. Never equate an action's process date with its effective/ex/pay date. Unknown coverage limits protection; it must not be silently narrowed to returned rows. Equally, old development exposure must not become a lifetime ban on a genuinely later, known non-overlapping interval.

Before any real reservation, reconcile existing provenance submissions, prepared-request/page events, published receipts, pending acquisitions and explorer exposure rows into an append-only legacy coverage inventory. Missing explorer rows are not clean history. Preserve original observations and uncertainty; do not backfill invented access times or erase old records. Later alias discoveries or revisions must extend the relation and invalidate conflicting protection rather than reset exposure. Generic imported bytes need a reviewed coverage/origin contract; arbitrary `put_bytes` callers cannot certify protected eligibility merely by choosing a new root or omitting metadata.

Pin the registry and ordinary/evaluator storage identities through the trusted supervisor configuration. Do not trust a caller-provided path or `access_class` string as the authority. Protect against ordinary callers opening the future evaluator root through `Provenance(other_root)` or copying a protected digest into the development namespace. A marker/directory convention can help cooperating clients refuse misuse, but it is not OS isolation or protection from the owner.

This increment can establish **guarded application access and conservative reservation accounting**. It cannot establish protected-data secrecy, a successful campaign, statistical validity or R13 completion. The repository's current actual D007/D008 observations remain development-exposed.

## Following evaluator increment

Add a distinct evaluator store and typed service after the gate is independently verified. It owns raw and partial provider responses, normalization, full-range admission, detailed failures, results and protected source-review records. Ordinary provenance readers, model packet builders, failure memory, dashboard routes and conversation contexts must have no supported lookup into that store. Shared journals contain only the release contract's approved control metadata, not data-bearing outcome details or readable protected-object references.

Persist one-use consumption **before** any protected page request, file read, inspection or calculation. Unknown access is consumed. A pre-access rejection remains unconsumed only when its final rejected intent and service access log establish that no acquisition request was emitted and no protected file opened. Crash recovery preserves uncertainty; exact replay is another attempt under the same frozen consumed invocation, not another final opportunity. Changed code, rules or observations create diagnostic lineage without restoring entitlement.

Issue persistent principals and record protected access across assignments and role changes. A protected-fact reviewer cannot select or revise the candidate for that reservation. Unknown identity continuity cannot be cured by minting a different role label. In the same-user Mac deployment these are cooperating-application controls: native agents and the owner retain filesystem authority. A stronger adversarial isolation claim requires a separately controlled OS/service boundary and demonstrated denied access; neither permissions nor labels alone establish it.

Release successful, failed and uncertain campaigns through the same predetermined category of lifecycle receipt and outcome-independent schedule. Keep numerical values and data-dependent diagnostics inside the evaluator. A later paper monitor visible to researchers, the dashboard or the owner is development exposure under D008; it cannot simultaneously serve as a blind final evaluation.

## Verification that would justify advancement

1. Race reservation creation against acquisition/import authorization in both orders. Exactly one compatible path proceeds; an interrupted intent still blocks overlap after restart. Test pagination and the gap between authorization and the first page.
2. Exercise every function and CLI route directly, including lower-level transport, ordinary artifact lookup, dataset import, admission, suite and broker entrypoints. Denied paths must not read protected bytes or call the fake transport; empty exposure queries must not bypass pending/unknown legacy evidence.
3. Cover alias changes, raw/adjusted revisions, boundary-date equality, warmup/final overlap, action process dates and global calendar scope. A demonstrably later non-overlapping interval remains eligible; unresolved identity/coverage refuses rather than guessing.
4. Inject crashes before intent commit, after commitment, after request emission, after partial bytes, and before publication. Verify the rejected-unconsumed proof rule, conservative unknown consumption and preserved attempt/budget/exposure history. A renamed candidate or changed dependency never resets consumed state.
5. Verify persistent-principal separation across role changes and credential reissuance. Test attempts to open the evaluator root through the ordinary store, import a known protected digest and put protected-derived diagnostics into shared outcomes, failure memory, status/docs or model packets.
6. Independently test fixed release shape and timing for success, failure and uncertainty. Inspect emitted bytes for synthetic protected prices, dates, identifiers, diagnostics and lookup references; regex screening alone is insufficient. Keep raw test fixtures synthetic and outside actual stores.

The current tests in `test_explorer.py`, `test_alpaca_data.py`, `test_alpaca_actions.py`, `test_provenance.py`, `test_research_workflow.py` and `test_research_packets.py` provide useful exposure, dispatch-order, tombstone, lease and strict-schema fixtures. They do not yet demonstrate these evaluator guarantees. New independent criticism, quality execution and scope review must identify the exact revision and distinguish fixture behavior from actual operational evidence.

## Existing authority and later decisions

The registry, mandatory access gates, separate namespace, conservative consumption and reviewer-selector separation implement accepted D008; they do not require another council merely because they need new modules. Choosing a new statistical estimand, worthwhile-effect threshold, horizon, calibration/error policy, financial model, stronger release permission or weaker isolation/recovery threat model is a substantive decision and needs the required independent perspectives and actual outside-model review. No universal 252-session, Newey–West or automatic promotion rule is already approved.

An actual historical access-control pilot comes only after synthetic and bypass acceptance: freeze its mechanical instrument/window rule and any random seed, verify application non-overlap, and freeze the integrity-only release schema before access. Unknown outside owner/model exposure remains disclosed; pilot failure stays consumed. A future performance campaign additionally needs an independently reviewed statistical plan and candidate freeze before its observations begin. Neither this proposal nor a successful gate test supplies those observations or completes R13, R14, external recovery, paper operation or live readiness.
