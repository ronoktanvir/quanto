## Acquisition request, receipt and normalized profiles

All field sets below are exact for the selected finite writer unless an optional field is named. Reject unknown additions from a known strict producer rather than silently dropping potential references. For an unknown producer, retain safe known references but report unsupported profile coverage. Strict duplicate-key/finite-JSON checks and aggregate limits apply throughout. ### Prepared requests are versionless

The current walker assumes every supported document has `schema_version`. These prepared objects do not. Make schema validation role/profile-specific; do not invent version1 or loosen every other profile.

- Bars/calendar prepared keys: `method,request,url,max_pages,max_total_bytes,max_total_seconds`. Require `GET`; page cap8 for bars or1 for calendar; byte cap8MiB and time cap60. Calendar request is exactly `start,end`. Bars request is exactly `start,end,symbol,adjustment,timeframe,feed,currency,asof`, with `adjustment` raw/all, `1Day,sip,USD,-`, canonical dates and the committed symbol grammar.

Require2MiB,1.0,true,`process_date_envelope`; request keys are exactly `symbol,start,end,region,data_quality,sort,limit`, with `us,all,asc,1000`. Its original submitted request contains only `symbol,start,end`.
- Check prepared request equals the receipt's normalized parameters and that retained URL route/query corresponds to the selected profile using pure parsing. Treat page tokens as bounded inert data; do not perform DNS/network access. A new parser should compare query pairs without discarding duplicates. Preserve the exact stored URL bytes independently of semantic comparison.
