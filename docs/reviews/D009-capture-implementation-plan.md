# D009 research-state capture implementation proposal

**Implement an offline, inert snapshot of the entire research database and the available content-object store, with explicit evidence omissions.** This first increment must not claim a complete project backup, off-Mac recovery, trusted freshness, or permission to resume work. It preserves uncertainty and exposure exactly as recorded. No application constructor, provider, scheduler or financial calculation runs during capture or verification.

Status: source-only proposal awaiting lead and independent contract review. Producer: `/root/d009_stage_a_builder`. Inspected repository revision: `955710036e41270b05bdf56964ae65a530869e98` on `feat/recovery-snapshots`. This inspection read source and the accepted D009 policy only; no production database, object, `.env`, private runtime file, recovery identity or provider account was opened. No fixture or actual snapshot has been executed for this proposal.

Subsequent implementation authorization narrows this proposal: the module is `quanto.recovery`, with `capture_research_snapshot(source_root, destination, *, limits=...)` and `inspect_research_snapshot(snapshot, *, expected_manifest_sha256=None, expected_event_head=None, limits=...)`. Destination is an explicit new directory outside the entire source root, superseding the earlier in-runtime layout paragraph below. The first candidate validates known typed database references only, retains all available canonical objects, and always reports `typed_closure_complete=False` and `full_recovery_accepted=False`; recursive document semantics remain an explicit omission. Unknown ordinary tables are preserved and identified as unsupported coverage, while altered known reference schemas refuse. This supersedes the proposal's broader suggestion to reject all unknown ordinary schemas. There is no CLI, key access, archive, upload or execution integration. The original proposed later work remains recorded below rather than being represented as implemented.

## Storage and ownership observed in source

| Storage or schema owner | Data to preserve or explicitly exclude |

| `research_broker.py` | Broker runs/configuration, aliases, stages, tool requests and parent-child bindings. |

| `conversations.py` | Separate `runtime/conversations.sqlite`, containing sessions/CSRF material, conversations, turns, messages, rate events, worker inbox and replies: excluded in this increment. Its cooperating calls also write shared research-budget state, which remains included. |

The nine research schema families define 40 named tables; `provider_allocations` is shared by two modules. Constructors create schema and triggers on demand, so absence of an unused family can be legitimate. Capture copies all existing database pages/tables, not a selected export of successful experiments. A versioned validator must recognize the present schemas and refuse unsupported schema changes rather than drop unknown data.

`Journal.__init__` changes journal mode, applies schema and creates triggers. `Provenance`, `FailureMemory`, workflow, broker and dispatcher initializers also perform DDL. They are unsuitable for an inert verifier. Use raw SQLite connections and pure validation functions instead. The current journal explicitly selects rollback mode `DELETE`; the proposal supports that observed source profile first and refuses unexpected WAL/other modes, without changing the source mode or attempting a checkpoint.

## Reference inventory and evidence closure

An artifact digest is not interchangeable with every 64-character hash. For example, submission `request_sha256` can describe bytes that `begin()` never stored, broker `code_sha256` hashes an identity document, and dispatch `body_sha256` hashes outbound request bytes. Code, event, packet-component and specification hashes do not automatically imply a file at `data/objects/<hash>.bin`.

Use a reviewed, versioned reference extractor, keyed by source table/column and supported document kind/version. Its first root set includes:

- `provenance_outcomes.details.artifact_refs`, including failed/invalid outcomes with retained evidence; relevant registered request references are interpreted by their actual receipt schema.
- Explorer dataset manifests and exposure dataset identities; suite run manifest/roster references and stored launch requests; comparison registration references.
- Workflow manifest/input references, assignment and intent input references, handoff document digests and nested artifact/reviewed/objection references, and effect-outcome artifact lists.
- Broker configuration, alias artifacts, stage records and tool requests; private model-response references; failure-disposition fix references when present.
- Supported acquisition event references, particularly prepared request objects and received raw pages for work that has no terminal provenance outcome yet.

From supported documents, follow their declared dependencies: acquisition raw pages/request/normalized receipts; dataset source/normalized bars/parent; admission sources, facts, usage review, independent calendar, semantic reviews and policy/refusal lineage; suite requests/members; broker context/proof/response/handoff objects; and failure-memory evidence. Detect cycles with a visited set; bound depth, references, document size and total work. Do not run existing domain validators that construct stores, record exposures, append events or query mutable live state.

For this first capture, copy **every available canonical content object except snapshot-tombstoned digests**, rather than trying to minimize the files to a recursively selected subset. This is a conservative superset: it preserves already-written unpublished/orphan evidence after a failed transaction and covers present dependencies even when a document is opaque. An orphan is not promoted to a published result. Unknown binary or private raw-response objects remain opaque bytes with a verified digest; content copying is not semantic validation or permission to transmit them elsewhere.

The extractor still matters: it distinguishes a missing required live dependency from a legitimate digest-only identity. Missing or corrupt mandatory live objects prevent a verified capture. A required tombstoned reference is an explicit unavailable-evidence entry; its bytes must not be copied or resurrected, and evidence completeness is false. Do not call a typed-reference check universal semantic closure: retain an explicit coverage version and report unknown document kinds or unresolved external dependencies. The full available-object inventory plus known-reference checks is the first bounded evidence claim; stricter complete-evidence acceptance requires all required document schemas and sidecars to be covered.

## Consistent capture without changing source state

Use three connections with distinct purposes: a source writer barrier, an independent read-only source for SQLite's online backup API, and a newly created private destination database. Never call `backup()` on the connection holding `BEGIN IMMEDIATE`; that same-connection pattern risks waiting on its own active write transaction.

1. Validate the exact project root, `runtime/research.sqlite`, `data/objects`, and all relevant path components through no-follow regular-file/directory checks. Reject source/destination overlap, symlinks, devices/FIFOs, unexpected hard links, unsafe ownership/modes and oversized inputs. Do not create a missing source database. Open the barrier connection with URI `mode=rw`, short bounded lock wait and no schema initialization.
2. Acquire `BEGIN IMMEDIATE` without issuing writes. This waits for a current cooperating writer and prevents subsequent writers. Verify rollback journal mode, supported schema shape and source-file identity without changing PRAGMAs that persist state. Do not require all research work to be terminal: unfinished work is part of the snapshot.
3. Open the independent source with `mode=ro`, establish its read snapshot, and run the SQLite online backup API into an exclusive mode0600 destination. Bound page steps, BUSY handling and elapsed time with a progress callback. Source and destination are never the same database. Reject rather than silently retry the whole capture after a deadline.
4. While the barrier remains held, read the copied database's tombstones and typed reference roots; enumerate canonical object names and copy each non-tombstoned object using descriptor-based, no-follow bounded reads. Verify SHA-256 against filename, record size, and check identity/size before and after the read. Reject raced bytes or unsafe entries. `.pending-*` leftovers are excluded as unpublished temporary files and counted explicitly; they are not copied or promoted.
5. Verify the copied database and object inventory, then recheck source database identity and event count/head against the captured cut. Release the read transaction and always roll back the barrier in `finally`, including timeout, cancellation and disk failure. No event or budget record is appended to production by the snapshot operation.
6. After all checks pass, fsync the snapshot files and write its final manifest/commit marker exclusively and last. An interrupted staging directory has no accepted manifest and cannot be restored or automatically resumed. Never overwrite an earlier generation or production file.

The barrier is sufficient for cooperating object publication because `put_bytes` publishes under the same database's write transaction. Publication may precede its eventual reference transaction, explaining orphans. `purge` is more subtle: it commits its tombstone before unlinking bytes outside that transaction. A purge already in flight may continue during capture, but it can remove only a digest already tombstoned at the captured cut; those bytes are excluded. A new tombstone cannot commit while the barrier is held. Test this exact ordering rather than assuming every unlink is inside a transaction. Direct filesystem-owner changes remain outside the cooperating-client guarantee and should be detected where possible, not described as impossible.

A database barrier does not revoke a provider request already authorized and sent, freeze all chat state, or make external side effects atomic with the snapshot. A captured reservation may still be `reserved` while the external result is unknown; preserve it exactly, report pending work and forbid effect replay. This increment remains offline and inert. Repeated online operation and restoration of scheduling authority require D009 Stage C.

Proposed initial bounds are a 64 MiB database, 16 MiB per object, 10,000 canonical objects, 256 MiB total copied bytes, a 2-second barrier-acquisition wait and a 15-second held-barrier deadline. These are proposed limits, not measurements of production. Exceeding a limit refuses without silently omitting files or extending a lock; a later reviewed revision can raise limits. Fixtures must prove timeout release so website/model accounting writers are not stranded behind a failed capture.

## Snapshot layout and inert verification

Use a fixed output parent under ignored `runtime/recovery/snapshots/`, with a random exclusive generation directory and mode0700 directories/mode0600 files. This is a distinct allowlist, never a recursive copy of runtime. Proposed layout: `research.sqlite`, `objects/<digest>.bin`, and `manifest.json`. Keep failed-staging diagnostics bounded and free of payloads; do not include the permanent identity, `.env`, credential files or arbitrary user-selected paths. No archive extraction is needed in the first increment.

The manifest declares format/version, capture start/end and cut identity, producer source hashes/repository revision, source schema fingerprint, exact database size/hash, sorted object sizes/hashes, counts, event count/head, tombstones/unavailable dependencies, reference-coverage version, opaque/unpublished objects, and explicit omission categories. Record all integer money and operational state through the unchanged database; manifest summaries must not replace it. Source-code hashes and a Git revision aid identification but are not copies of historical source, Python packages or independent audit evidence.

The verifier accepts only this layout, rejects duplicate/unknown/unsafe manifest paths, extra payload files, symlinks, hard links, SQLite sidecars, missing files and byte-limit violations, and checks every byte count/hash. Open only the completed, self-contained snapshot with SQLite `mode=ro` and `immutable=1`, never the live source with `immutable=1`. Disable trusted schema and extension loading; use query-only operation and a deny-write authorizer. Reject unsupported virtual tables/views/schema additions rather than querying them. Bound SQL work and rows.

Run `integrity_check` and `foreign_key_check`, validate the supported schema fingerprint, and recompute the event chain with a pure read-only implementation of the current event hashing rules. Compare count/head with the manifest and an optional caller-supplied expected checkpoint. The event chain verifies events, not every materialized table's semantic derivation, and a self-contained manifest cannot prove freshness against a malicious account or local owner. Full database hashing detects later byte changes relative to that manifest; it does not establish an independently trusted original.

Return a bounded report with `snapshot_bytes_verified`, `database_integrity_verified`, `event_chain_verified`, and `declared_references_verified`, alongside `project_backup_complete=False`, `chat_recovery_included=False`, `external_audit_sidecars_included=False`, `off_mac_recovery_verified=False`, and `execution_enabled=False`. Evidence completeness must remain false whenever tombstoned, unknown-schema or excluded dependencies remain. Verification never changes reservations, marks pending effects complete, releases holds, refreshes leases, opens a model connection, restores production or starts a worker.

## APIs and implementation boundaries

Propose one focused module, `quanto.recovery_snapshot`, with `capture_research_snapshot(root, *, limits=...) -> CaptureReceipt`, `verify_research_snapshot(snapshot_dir, *, expected_manifest_sha256=None, expected_event_head=None, limits=...) -> VerificationReport`, and private pure schema/reference/event helpers. No generic “backup any directory” option, credentials argument, network adapter, model client, scheduler callback, restore-to-production function or automatic upload belongs in this increment.

Capture owns the fixed generation path and returns its manifest identity; verification is separately callable and read-only. Add explicit CLI commands only after the module contract passes independent criticism/quality. A later pack/encrypt/upload layer must consume an exact verified manifest, recheck bytes, use the separately confirmed recovery recipient and its reviewed data-use scope, and retain the later transfer/restore evidence. It must not regenerate a key or expand the source allowlist.

## Meaningful tests required before implementation acceptance

- Build an invented database containing reserved/uncertain/overage amounts, consumed dispatches, prior-day purpose allocations, leased jobs, pending submissions/effects, exposure history, failed suite members and private-response references. Capture and compare every table row/schema item; verify no reset, settlement or invented terminal record.
- Run real SQLite rollback-mode concurrency fixtures with separate connections/processes: an active writer blocks capture within the deadline; a writer after the barrier cannot publish; backup on the independent reader finishes; cancellation/disk error releases the barrier. Test the proposed sequence under the supported Python/SQLite versions, not only mocks.
- Interleave `put_bytes` publication and later reference commit, including a rollback orphan. Retain present orphan bytes without claiming publication. Interleave tombstone-then-delayed-purge before and during capture: never copy tombstoned bytes or restore their availability; never accept a missing required live object.
- Test each typed root family, supported nested references, cycles, duplicate/malformed JSON and digest-only identities that deliberately have no object. Include pending acquisition raw pages, unpublished private model responses and legacy report paths so terminal outcome lists are not mistaken for the whole evidence graph.
- Reject missing/corrupt objects, digest/name mismatch, unsupported database schemas/modes, bad event chains, foreign-key violations, schema drift, oversized databases/objects/counts and deadline exhaustion. Tombstoned dependencies produce named limitations rather than silent “complete” status.
- Reject traversal, absolute/colliding/duplicate manifest paths, source/output overlap, linked directories/files, FIFOs/devices, extra files, unexpected sidecars and incomplete publication. Read-only verification leaves directory contents and database bytes unchanged and never calls constructors, model/broker functions or worker methods.
- Exercise two successive snapshots with different event heads. An explicit expected head/manifest mismatch refuses; without a trusted external checkpoint, an older authentic snapshot is labeled internally valid without claiming it is latest. No automatic retry, generation substitution, deletion or restore occurs.

## Explicit omissions and next decision

Excluded now: chat database and CSRF/session continuity; `runtime/reviews`, council CLI transcripts and accounting sidecars, D007/D008 private audit harnesses and actual-run inspection outputs, Runpod receipts and cost-monitor state, five-minute website snapshots/status, legacy `artifacts/synthetic` payloads, local configuration/credentials, permanent recovery identities, Git history and installed dependencies. Referenced source documents already stored as content objects are included; hashes or paths pointing outside the object store do not cause arbitrary files to be copied. Summarize detected external references by bounded category/digest, without exposing raw paths or private rationale in public output.

These exclusions mean that the first result is a database-and-object inspection snapshot, not a self-sufficient replay environment or complete evidentiary archive. The shared research ledger preserves chat-related spending conservatively, but cannot recreate chat turns or reconcile a cross-database transition by itself. Later acceptance must name the required source/audit sidecars and their stable capture/privacy contract, confirm off-Mac key retrieval and account/2FA recovery, review source-use rights for encrypted external retention, and pass an isolated restore. The lead should approve or narrow this exact scope before product implementation begins.

## Producer implementation checkpoint after contract acceptance

The lead authorized the narrowed `quanto.recovery` candidate and its synthetic tests. The first frozen module (`0688bd81cdcc903df31629bd1d2d1cb9a862b0a6f7e88751955cdd3d146955a4`) passed30 producer cases. Independent criticism then reproduced four defects: suite-member request hashes were treated as mandatory object files; manifest timestamps/producer/consistency/pending-count fields lacked complete validation; a source database could grow beyond the configured bound before the guarded audit; and opening the writable guard before the read-only reader could recover a hot rollback journal and change the source. Those findings and baseline evidence remain with the independent reviewers.

The revised module establishes a read-only SHARED snapshot before acquiring the separate writable guard, rechecks source size/identity under that guard before audit or backup, validates manifest metadata and exact typed state, and preserves suite-launch request hashes as inline identities. This ordering supersedes steps2–3 of the original proposed sequence. A hot-journal fixture uses a deliberately crashed SQLite subprocess: a disposable copy demonstrably recovers, while capture refuses the original and leaves its database and journal bytes unchanged. Existing-writer contention may cause bounded refusal; capture never resolves it by releasing the read snapshot and silently retrying.
