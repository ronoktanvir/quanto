# D009 storage architecture perspective

**Use one small standard Runpod volume as an encrypted recovery destination, with an explicit cooperative-writer threat model. Do not call the volume immutable or treat a successful upload as scheduler acceptance.** This recommendation separates recoverability, checkpoint freshness and protection against a privileged remote writer.

Reviewer: `/root/d009_storage_architecture`, 2026-11-02. This is one independently briefed architecture perspective, not an accepted D009 decision or implementation review. The reviewer inspected public repository source and official documentation only. No credential, account, actual database, private financial artifact or model response was accessed; no resource was created and no data was transferred.

## Evidence and proposed footprint

Runpod documents standard storage at USD0.07/GB/month below 1 TB, expandable but not shrinkable. Its current creation example uses `POST https://api.runpod.io/v2/network-volumes` with `name`, `size` and `dataCenter`. Unfunded storage may eventually be terminated. [Network volumes](https://docs.runpod.io/storage/network-volumes)

Direct S3 access needs no Pod. US-CA-2 is listed, with endpoint `https://s3api-us-ca-2.runpod.io/`. Separate S3 access/secret credentials are required. Basic put/get/head/list and multipart operations exist; versioning, Object Lock, bucket policies/ACLs and bucket-encryption APIs do not. Single puts must be below 500 MB. Large directory listings/sync have documented limitations. [S3 compatibility](https://docs.runpod.io/storage/s3-api) Management and S3 credentials are distinct. [Credentials](https://docs.runpod.io/get-started/credentials)

The lead reports an API minimum of 10 GB and metadata-only local directory totals of runtime 3.44 MB, data 6.70 MB and artifacts 5.8 KB; these observations support the smallest allocation, subject to the final payload manifest. The lead also reports an authenticated read-only catalog observation: US-CA-2 currently offers only HIGH_PERFORMANCE, while US-WA-1 and US-KS-2 offer STANDARD. These account and filesystem observations were not independently reproduced by this reviewer. They change the initial location preference from California to Washington without changing the architecture. Future capacity should cover three complete generations, staging and at least 25% reserve. A 50 GB standard allocation would be USD3.50/month, but buying unused capacity is unnecessary. Confirm the actual tier and size in the create response; do not substitute a premium tier or rent compute. US-KS-2 is a fallback only after the same preflight.

The owner's newer USD50 authorization is a total Runpod setup ceiling, not a reason to consume it or change the model budgets. Charges continue after a local process stops. Record the start time, allocated rate, cumulative account cost attributable to this resource, remaining authorization and renewal deadline; alert before the limit rather than pretending a local flag stops provider billing. Do not delete the only recovery copy automatically when the allowance ends.

## Snapshot that can actually be restored

Quanto's `Journal` uses SQLite with DELETE journaling and FULL synchronous writes. `verify_events(expected_head)` verifies the event chain and an exact expected head; its own contract explicitly excludes arbitrary materialized-table validation. `Provenance` stores the research database in `runtime/research.sqlite` and content objects in `data/objects`. Conversations have a separate SQLite database. The code has no complete backup/restore coordinator yet. Relevant inspected source: `src/quanto/ledger.py`, `src/quanto/provenance.py`, `src/quanto/conversations.py`; existing suffix-removal test: `tests/test_ledger.py`.

Create a manifest-driven snapshot, not a recursive copy of the repository:

1. Enter a coordinated checkpoint boundary that prevents new research effects, account-changing chats and artifact deletion during capture. Either quiesce every relevant writer or explicitly capture and reconcile its database; independent copies of several live databases are not one atomic application snapshot.
2. Use SQLite's backup API for each database into a new private staging directory. The API provides a consistent database snapshot, unlike an unlocked filesystem copy. [SQLite backup API](https://sqlite.org/backup.html) Read the research event count/head from the resulting snapshot, then verify its chain and integrity before making claims about it.
3. Include the exact referenced content-object closure, pending/failed attempt evidence, audit harnesses needed for reproducibility, budget and exposure state, source revision/lockfiles and reviewed restore metadata. Missing referenced objects fail the snapshot. Tombstones remain meaningful; do not restore intentionally removed material from older generations as current evidence.
4. Reject symlinks, traversal, unexpected file types and unbounded members. Use explicit paths and content digests. Exclude `.env`, provider credentials, OAuth sessions, private decryption keys, browser profiles, caches and unrelated files. Classify and review the encrypted backup payload before upload; provider rights remain applicable even when encryption hides the content.
5. Generate a bounded canonical manifest containing snapshot ID, parent manifest digest, schema/source identities, event count/head, exact database/object hashes, sizes, capture times and whether the state is operationally complete or uncertain. A hash of the whole database protects materialized state that event verification alone does not cover.
6. Encrypt locally with an established portable format such as age, using a dedicated public recipient for the uploader. Keep the decryption identity outside the backup and preserve an owner-controlled recovery copy outside this Mac. age supports recipient-based encryption and separate identity-based decryption. [age project](https://github.com/FiloSottile/age) Test recovery-key usability without exposing the key to chat, logs or Git.

Use a small number of independently authenticated encrypted chunks below the single-put limit, rather than thousands of loose files or one unbounded archive. Names should reveal only opaque IDs and ciphertext digests. The encrypted manifest describes order, lengths and hashes; the manifest is uploaded last. Keep temporary plaintext private and short-lived. No encrypted object is considered committed until a fresh download verifies its ciphertext hash and a clean restore validates the decrypted manifest and content.

## Freshness and rollback are distinct guarantees

The accepted D008 policy requires an external checkpoint before further irreversible effects when the previous boundary is not safely recorded. A five-minute website snapshot is not that checkpoint. Its status capture interval must remain a separate dashboard observation.

For a future scheduler, prepare the exact effect ID, reservation and one-use intent locally, then preserve that intent externally **before dispatch**. Preserve the resulting consumed/uncertain/settled state externally before allowing a later effect. A crash between send and result leaves an uncertain attempt and its full hold; recovery must not replay it or grant a new allowance. A post-send-only backup can lose the only evidence of a request sent immediately before a crash. No storage upload changes these financial semantics.

Runpod can serve as an external high-water record under the declared assumptions that the authenticated account remains available, historical objects are not maliciously deleted or rewritten, and one cooperating writer owns the stream. Use unique generation keys, digest chaining, a pinned volume/account/region identity and direct verification of the selected generation. Treat any mutable `latest` pointer as a cache, not evidence. Concurrent writers, divergent children, missing expected generations, stale lists and timeouts must stop advancement rather than choose a convenient branch. If upload acknowledgement is uncertain, query the exact object key and compare bytes before any new write; do not blindly create another paid resource or overwrite evidence.

These application rules do **not** create write-once storage. The same remote credentials can delete or replace objects, and signatures alone cannot distinguish an authentic old snapshot from the authentic newest snapshot. If the required threat model includes a malicious account writer, compromised Mac credentials, remote suffix deletion or provider rollback, a separately controlled high-water witness or a destination with independently enforced retention is still required. A receipt kept only beside the local database, or under the same deletable remote authority, does not establish that stronger guarantee. D008 need not be silently expanded to claim this stronger threat model; the lead must state exactly which boundary is accepted and test it.

## Gates and acceptance evidence

Before provision: finish the required significant-decision reviews; verify offered size/tier/region and rate; measure the selected payload without printing private contents; record the resource's spend cap and lifecycle plan. Reconcile an uncertain create response by listing/identifying the exact attempted resource before any retry. Do not buy a duplicate.

Before project-data transfer: establish pinned remote identity and separate S3 credentials, a valid encryption recipient and off-Mac recovery-key custody; finalize the path allowlist and retention policy. A synthetic encrypted canary may first prove put/get/decrypt and deletion behavior without exposing project data. Absence of Object Lock must remain recorded rather than tested away.

Before calling the backup usable: restore the downloaded encrypted generation into an isolated directory with network/model dispatch disabled; verify archive safety, all hashes, database integrity and event head, full uncertain reservations, consumed intent IDs, exposure history and pending-job fencing. Do not reset budgets, revive old leases or replay sends. Exercise missing chunks, corrupt ciphertext, wrong keys, stale generations, divergent history, upload interruption and destination unavailability. Recovery must leave the current production workspace untouched until deliberate cutover.

Before unattended scheduling: implement the pre/post-effect checkpoint barrier, bounded failure behavior, restart and rollback tests, and observed sustained operation. Expose last backup attempt, last verified remote generation, last tested restore, next attempt and blocking reason separately. An initial successful backup closes only the corresponding recovery increment; R14, protected evaluation, prospective paper and live activation remain incomplete.

## Recommendation boundary

The smallest useful purchase is the measured encrypted-backup pilot, not a cloud workstation. The central limitation is authority: external storage reduces dependence on this Mac, while a trustworthy latest-state guarantee depends on who can erase the remote history. Retain that distinction in the implementation, dashboard and acceptance report.
